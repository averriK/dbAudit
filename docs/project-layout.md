# Project layouts

dbAudit has two input contracts. Both take a single directory — the
**data root** passed to `--project` — but they expect different trees
under it:

- **Geochemistry** (`dbaudit geochemistry`, or no subcommand): inputs
  under `raw/lab/` and `raw/assay/`; outputs under `proc/`.
- **Monitoring** (`dbaudit piezometer`, `dbaudit inclinometer`): inputs
  under `source/`; outputs under `raw/`, `db/` and `audit/`, all three
  owned and regenerated by the tool.

## Geochemistry data root

```
<DATA_ROOT>/
  raw/
    lab/          # input: lab certificate CSVs (searched recursively)
    assay/        # input: one assay/client CSV
  proc/           # output: created by the run
    index.csv     # analyte metadata per certificate
    lab.csv       # long-format lab values
    client.csv    # long-format assay values
    log.csv       # event log
```

`raw/lab/` must exist before the run; a missing lab folder stops the
run:

```
lab.dir not found: <DATA_ROOT>/raw/lab
Execution halted
```

`proc/` is created if absent. The three folder names are defaults
(`.dbauditPathDefaults` in `R/dbAudit.R`) and can be overridden per run
with `--lab-dir`, `--assay-dir` and `--proc-dir`, all interpreted
relative to the data root. This runs the synthetic-A fixture in its
as-shipped layout (`raw/` + `assay/`, no `raw/lab` level):

```bash
dbaudit geochemistry --project <DATA_ROOT> --lab-dir raw --assay-dir assay
```

### Assay file selection

The assay CSV inside the assay folder is selected deterministically, in
this order (`.chooseAssayFile()` in `R/dbAudit.R`):

1. `_Assay_Comp.csv`, if present.
2. Otherwise `AAQ_Sample_Assay.csv`, if present.
3. Otherwise every `*.csv` in the folder is tested against the known
   assay header formats; exactly one match is used.
4. More than one match stops the run and lists the candidates.
5. No match but **exactly one CSV** in the folder: that file is used
   even though format detection was inconclusive.

An empty folder, or several CSVs none of which match, stops the run.
`--assay-file <PATH>` bypasses detection; it accepts an absolute path or
a basename resolved under the assay folder.

## Where each subcommand looks

Every subcommand looks for its own child of the input directory. One rule
covers the three domains:

```
<DATA_ROOT>/data/GEO/lab/       laboratory certificates      geochemistry
<DATA_ROOT>/data/GEO/assay/     the client assay table       geochemistry
<DATA_ROOT>/data/PCG/<Site>/    Casagrande spreadsheets      piezometer
<DATA_ROOT>/data/PCV/<Site>/    vibrating-wire spreadsheets  piezometer
<DATA_ROOT>/data/INC/<Site>/    inclinometer surveys         inclinometer
```

so the commands carry no path options at all:

```bash
dbaudit geochemistry --project <DATA_ROOT>
dbaudit piezometer   --project <DATA_ROOT>
dbaudit inclinometer --project <DATA_ROOT>
```

The three domains share one root: each writes its own products and reads
only its own child.

For monitoring, `<Site>` is not decoration — the site and the hole of every
reading are read from that path.

### Layouts already in use

Adding the rule did not retire the layouts that came before it, and no
project has to move anything:

| Layout | Still resolves |
|---|---|
| `raw/lab/`, `raw/assay/` | yes — the historical geochemistry contract |
| `source/<ID>/<Site>/` | yes — the historical monitoring contract |
| `data/<ID>/<Site>/` | yes |

A directory named explicitly with `--lab-dir`, `--assay-dir` or
`--source-dir` always wins over the convention.

## Monitoring data root (piezometer + inclinometer)

The user creates and maintains exactly one subtree: `source/`, grouped
by instrument id, then site. Files are discovered recursively below each
id.

```
<DATA_ROOT>/
  source/                  # input: the only user-owned subtree
    PCG/<Site>/…           # Casagrande piezometer workbooks (.xlsx)
    PCV/<Site>/…           # vibrating-wire piezometer workbooks (.xlsx)
    INC/<Site>/<Hole>/…    # inclinometer survey exports (.csv)
```

A missing `source/` stops the run:

```
Error: source.dir not found: <DATA_ROOT>/source
Execution halted
```

Every file under the source root is accounted for: the source census
compares the tree against the files actually parsed and logs a
`MISSING` error for any file that never parsed (for example, a stray
copy under `source/backup/`).

The runner creates everything else. After `dbaudit piezometer` followed
by `dbaudit inclinometer` on the Vega fixture:

```
<DATA_ROOT>/
  raw/                     # output: normalized per-sensor tables
    PCG/<Site>/<Hole>/<Sensor>/   data.csv, header.csv, index.csv
    PCV/<Site>/<Hole>/<Sensor>/   data.csv, header.csv, index.csv
    INC/<Site>/<Hole>/<Sensor>/   data.csv, index.csv
  db/                      # output: one database table pair per id
    PCG.data.csv  PCG.index.csv
    PCV.data.csv  PCV.index.csv
    INC.data.csv  INC.index.csv
  audit/                   # output: audit products + event log
    PCG.audit.csv  PCV.audit.csv  INC.audit.csv
    PCG.reject.csv           # gate rejections
    PZ.data.csv  PZ.index.csv
    log.csv
```

## The monitoring runners are destructive

Each monitoring run **deletes and regenerates** `raw/<ID>` for the ids
it processes and **reinitializes** `audit/log.csv`. Consequences:

- Nothing you place under `raw/`, `db/` or `audit/` survives a run.
  User material belongs under `source/` only.
- Running `dbaudit inclinometer` after `dbaudit piezometer` on the same
  data root leaves `audit/log.csv` with only the INC rows; the
  piezometer events are gone. Archive `audit/` products you need to
  retain before re-running the other contract.

## Who creates what

| Path | Contract | Owner | Missing at run start |
|---|---|---|---|
| `raw/lab/` | geochemistry | user | hard error |
| `raw/assay/` | geochemistry | user | hard error (`assay.dir not found`) |
| `proc/` | geochemistry | tool | created |
| `source/` | monitoring | user | hard error |
| `raw/`, `db/`, `audit/` | monitoring | tool | created; regenerated on every run |
